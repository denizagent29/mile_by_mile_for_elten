# Мультиплеер «Миля за милей» — проект

Статус: черновик. Давид Пипер переделывает сигнальный протокол Elten («will be available in Elten 3.0»).
Текущий API уже есть в 3.0.1 — на него и ориентируемся, но не кодим до утверждения протокола.

Скоуп v1: игра **по нику**, без общего лобби. Лобби с комнатами — открытый вопрос, ждём ответа Давида (см. конец).

## Транспорт — что умеет Elten 3.0.1

- Отправка: `Program#signal(user, packet)` — JSON-пакет (Hash/Array/String/Integer/nil/boolean) юзеру по нику.
- Приём: колбэк `Program#signaled(user, packet)`; `user` — ник отправителя. Переопределяется в классе приложения.
- Доставка: store-and-forward через сервер EltenLink. Отправитель шлёт сигнал → сервер кладёт в очередь → клиент получателя забирает при статус-поллинге (по умолчанию ~2 с, настраивается 1–15 с).
- Маршрутизация по appid из манифеста (`ce5cff0e-6a9e-43da-afb3-d050b0ffc4ae`). Оба игрока должны запускать один и тот же билд.
- **Офлайн-доставки нет**: сигнал доставляется, только если приложение — активная сцена (`$scene`). Пришёл, пока приложение закрыто, — теряется навсегда.
- Проверка собеседника: `EltenLink::Profiles.card(EltenLink.client(self), nick)` → существует ли и **онлайн ли** (поле `status.online`).

## Жизненный цикл партии

1. **Создание (хост).** Форма создания → поле «Ник соперника». Перед отправкой проверка карточки:
   - юзер не существует → «Нет такого пользователя»;
   - офлайн → «Пользователь не в сети» (можно подтвердить вручную).
2. **Приглашение.** Хост шлёт `invite` и показывает «Ждём `<ник>`…» с таймаутом (~60 с). Пока ждёт — подпирает проверкой online.
3. **Ответ.** Приглашённый (приложение открыто) видит «`<ник>` приглашает вас: 3000 миль, 1 колода» → Принять / Отклонить.
4. **Подключение.** `accept` от приглашённого = факт входа: хост берёт ник из поля `sender` и сверяет с приглашённым. `decline` → «Отказался», комнату закрыть.
5. **Старт.** Хост шлёт `start` с настройками, **сидом колоды** и первым ходящим. Оба клиента строят идентичную игру и запускают движок.
6. **Ходы.** Ходит тот, кому по движку принадлежит ход: играет локально → шлёт `move` сопернику → тот применяет к своему движку. Порядок определяется самим движком (удержанный ход за защиту / «пропуск хода» дают серию ходов у одного — соперник просто применяет каждый пришедший `move`).
7. **Финиш.** `finish` (результат) — оба показывают итог. (Онлайн-таблица рекордов — позже, через `leaderboard`.)

## Протокол сообщений

Все пакеты — JSON-объекты с обязательным полем `room` (строка-ид партии, UUID). Пакеты с чужим/неизвестным `room` игнорируются (поздние, чужие, устаревшие).

| type | от → к | поля | смысл |
|---|---|---|---|
| `invite` | хост → соперник | room, variant, distance_target, deck_mode, deck_copies | приглашение |
| `accept` | соперник → хост | room | принято |
| `decline` | соперник → хост | room | отказ |
| `start` | хост → соперник | room, seed, first | старт |
| `move` | текущий → другой | room, card_index, target | ход |
| `finish` | хост → соперник | room, result | итог |
| `bye` | любой → другой | room | выход |

- `move`: `card_index` — индекс карты в руке ходившего (колоды и руки у обоих одинаковые), `target` — `"self"` / `"opponent"` (или nil, если карта не требует цели). Приёмник воспроизводит `game.play(hand[card_index], target:)` — результат должен совпасть, потому что движки идентичны.
- `result` в `finish` — для подтверждения: победитель, дистанция. Расхождение с локальным движком = признак рассинхрона (см. «Анти-чит»).

## Правки движка (нужны для мультиплеера)

Движок детерминирован, кроме двух несидированных случайных точек:

1. `Deck#shuffle!` (`deck.rb:17`) — `@cards.shuffle!` без сида.
2. `Game#initialize` (`game.rb:31`) — `@current_index = rand(@players.size)` — кто ходит первым.

План: `Game.new(..., seed:)`; внутри один `Random.new(seed)` для обеих точек (тасовка колоды/колод и первый ход). Тогда один и тот же `seed` у хоста и соперника даёт идентичную партию.

Дополнительно:
- метод воспроизведения чужого хода по `card_index` + `target` (тонкий обёртка над `game.play`);
- `random` в другие места движка (бот-режим, звуки, UI) не влияет на партию — их не трогаем.

## Открытые вопросы (ждём Давида)

- **Лобби и комнаты.** Хочется общий список комнат: «3000 миль, Дениз Синджар, в ожидании…». Кандидат — серверная таблица `rooms` (`server_table`): `{host, distance, deck, status, created_at}`; заход в комнату = `invite` хосту. Главная проблема — **удаление комнаты при пропаже хоста** (интернет пропал — кто почистит строку?). Идеи на обсуждение:
  - TTL: при показе списка клиент фильтрует комнаты старше N минут и удаляет протухшие;
  - зашедший не дождался `accept` → помечает комнату мёртвой / удаляет;
  - серверный TTL на строках таблицы, если Давид такое даст.
- **Друзья.** Приложение не видит список друзей — только ники. Если в новом протоколе появится презенс/друзья — приглашение из списка, иначе по нику.
- **Реконнект.** Сигнал теряется, если соперник закрыл приложение. Таймауты «ждать / выйти»; доработка по факту.
- **Анти-чит / рассинхрон.** В v1 доверяем обоим локальным движкам. При подозрении — периодический `state`-чекпоинт (сверка движков). Реализуем, если понадобится.
