# Мультиплеер «Миля за милей» — проект

Статус: реализовано на `EltenAPI::Communication` (Elten 3.0.2 RC 1, `src/eapi/communication.rb`, коммит b2fb3c7).
Старый транспорт `Program#signal/signaled` с поллингом ~2 с и офлайн-потерей пакетов полностью заменён.

Скоуп v1: игра **по нику**, без общего лобби. Лобби возможно на `public_sessions` (см. «Открытые вопросы»).

## Транспорт — EltenAPI::Communication

- Создание сессии (хост): `endpoint.create_session(metadata: settings_payload, capacity: 2, encryption: 192)`. `metadata` — JSON-строка с настройками партии, попадает приглашённому как `invitation.session_metadata`.
- Приглашение: `session.invite(nick)` → `OutgoingInvitation`; статус поллится (`:pending` → `:accepted` / `:rejected` / `:cancelled`).
- Приём (гость): `endpoint.on_invitation { |inv| ... }`; принятие — `invitation.accept` (возвращает `Session`), отказ — `invitation.reject`.
- Сообщения: `session.send_reliable(JSON.generate(packet), to:)` — надёжная доставка с шифрованием 192-бит. Приём — `session.on_reliable { |msg| msg.data }` (расшифрованная строка).
- Колбэки сессии: `on_participant_left(participant, reason)`, `on_closed(reason)`. `participant.user` — ник.
- Выход: хост закрывает сессию целиком (`session.close`, только owner), гость выходит сам (`session.leave`). Обе стороны получают `on_closed`.
- Доставка колбэков — на главном потоке из `Communication.tick` (`src/ui/loop.rb:81`): состояние кладём в `@inbox` и поллим из Runner-циклов — гонок нет.
- `metadata` у гостя доступна как `invitation.session_metadata` (JSON: variant/distance_target/deck_mode/deck_copies).

## Жизненный цикл партии

1. **Создание (хост).** Форма создания → поле «Ник соперника». `create_session(metadata: настройки)` → `session.invite(nick)`. Пока `invitation.status == :pending` — показ «Ждём `<ник>`…», таймаут ~60 с (Runner `after(60)`, отмена по Esc).
2. **Ответ.** Гостю приходит приглашение: «`<ник>` приглашает вас: 3000 миль, 1 колода» → Принять / Отклонить. Отказ → `invitation.reject`.
3. **Подключение.** `invitation.accept` у гостя → `status == :accepted` у хоста; вход фиксируется, когда `session.participants.size >= 2`. Хост строит игру, шлёт `start`.
4. **Старт.** Хост шлёт `start` с сидом колоды и первым ходящим. Гость ждёт `start` (таймаут 120 с), строит игру и сверяет `first` (разница стартового сида у гостя — 1).
5. **Ходы.** Ходит тот, кому по движку принадлежит ход: играет локально → шлёт `move` сопернику → тот применяет к своему движку. Порядок определяется самим движком.
6. **Финиш.** Оба движка финишируют одинаково (сид один). `bye` — вежливый выход до/после финиша; хост делает `close`, гость — `leave`.
7. **Teardown.** `teardown_session` (идемпотентный) в конце любой партии: хост → `close`, гость → `leave`, `@session = nil`.

## Протокол сообщений

Все пакеты — JSON-объекты по надёжному каналу сессии. `room` не нужен: сессия Communication сама изолирует поток от чужих/устаревших пакетов.

| type | от → к | поля | смысл |
|---|---|---|---|
| `start` | хост → гость | seed, first | старт |
| `move` | текущий → другой | card_index, target | ход |
| `bye` | любой → другой | — | выход |

- `move`: `card_index` — индекс карты в руке ходившего (колоды и руки у обоих одинаковые), `target` — `"opponent"` или nil (карта без цели). Приёмник воспроизводит `game.play(hand[card_index], target:)` — результат совпадает, движки идентичны.
- Расшифровка пакета: `JSON.parse(msg.data.to_s.dup.force_encoding(UTF_8))`.
- Прерывание партии: `on_participant_left` / `on_closed` во время ожидания хода соперника → «Соперник вышел», `:aborted`.

## Правки движка (сделаны для мультиплеера)

Движок детерминирован, кроме двух несидированных случайных точек:

1. `Deck#shuffle!` (`deck.rb:17`) — `@cards.shuffle!` без сида.
2. `Game#initialize` (`game.rb:31`) — `@current_index = rand(@players.size)` — кто ходит первым.

Реализовано: `Game.new(..., seed:)`; внутри один `Random.new(seed)` для обеих точек (тасовка колод и первый ход). Один `seed` у хоста и гостя даёт идентичную партию; у гостя `seed + 1` (первый ходящий меняется на 1).

## Тестовая инфраструктура

`dev/harness_mp_smoke.rb` — two-sided smoke: хост и гость как две UI-инстанции в отдельных потоках, соединённых фейковым Communication-транспортом (in-memory). Запуск: `ruby dev/harness_mp_smoke.rb [N]`. Проверяет: оба движка финишируют, ходы идут в обе стороны, `start` доходит до гостя, позиция победителя совпадает. Ориентир: 10/10 партий в синке.

## Открытые вопросы

- **Лобби и комнаты.** В Communication есть `public_sessions` + `join(public_session)` — кандидат на общий список комнат. Открыто: фильтрация протухших лобби (кто чистит при пропаже хоста).
- **Реконнект.** `on_closed` / `on_participant_left` покрывают внезапный выход соперника. Полноценный реконнект (вернуться в незаконченную партию) — не в v1.
- **Анти-чит / рассинхрон.** В v1 доверяем обоим локальным движкам. При подозрении — периодический `state`-чекпоинт (сверка движков). Реализуем, если понадобится.
